# Notion Database Filter System — Exhaustive Reference (for 1:1 clone parity)

> Scope: Everything about Notion's database **filter** system as of the current product (2026). This document combines the **UI operator labels** (what users see) with the **API operator identifiers** (the machine-level truth that the UI mimics). Where the UI exposes something the public API does not (and vice versa), it is called out explicitly.
>
> Primary sources:
> - Notion Help — *Database views, filters, sorts & groups*: https://www.notion.com/help/views-filters-and-sorts
> - Notion Help Center — *Database views* category: https://www.notion.com/help/category/database-views
> - Notion API — *Filter data source / database entries* (operator ground truth): https://developers.notion.com/reference/filter-data-source-entries (new) and https://developers.notion.com/reference/post-database-query-filter (legacy, still lists all conditions)

## 0. Key architectural facts (answers to combining / per-view / interaction questions)

These are established up front because they govern the whole system.

### 0.1 Filters are PER-VIEW
- Each database **view** has its own independent settings. From the help doc: *"Each database view has its own settings. Settings applied to one database view won't be applied across all other database views automatically."*
- Adding/removing/editing a filter on one view does **not** affect any other view of the same database.
- When editing a filter you get a **"Save for everyone"** toggle:
  - **Save for everyone ON** → the filter is persisted to the view for all collaborators who can see that view.
  - **Save for everyone OFF** → the filter applies **only to you** (a personal/local override on that view). Other people see the view without your filter.
- Linked databases: a *linked* view is still its own view with its own filters; it does not mutate the source database's other views.

### 0.2 How multiple filters combine — AND / OR, groups, nesting
- **Simple filters**: multiple simple filters are combined implicitly. The bar reads **"Where all of the following are true"** (AND) — simple filters are ANDed together. (In the advanced editor you can flip the top-level connector to **"any"** = OR.)
- **Advanced filter / filter groups**: *"You can create more specific database views and combine AND and OR logic by using filter groups."*
- **Nesting depth limit**: **Filter groups can be nested up to THREE layers deep** (per the help doc verbatim: *"These can be nested up to three layers deep!"*).
  - Note: the **public API** documents compound nesting *"up to two levels deep"* — this is an API limitation, not a UI limitation. The **UI allows 3 levels**. For 1:1 UI parity, implement **3 levels** of nesting.
- Within any group/level, a single connector applies to all direct children: either **all** (AND) or **any** (OR). You choose "all"/"any" per group. You cannot mix AND and OR as siblings at the same level — to mix, you introduce a nested group.
- UI presents two distinct actions in the filter editor:
  - **"Add filter"** — adds a single condition (a leaf) to the current level.
  - **"Add filter group"** — adds a nested group (a new level) whose children have their own all/any connector.
- Turning a simple filter into an advanced one: open a filter chip → **•••** → **"Add to advanced filter"**. This converts the simple filter bar into the full advanced group editor.

### 0.3 Filters vs Sort vs Group (independent, composable stages)
- **Filter**, **Sort**, **Group**, and **Sub-group** are separate view settings and are applied independently:
  - Conceptual pipeline: **Filter (which rows are visible) → Group/Sub-group (bucketing) → Sort (order within, and group order)**.
  - Filtering removes rows first; grouping then buckets only the surviving rows; sorting orders rows within groups (and groups themselves can be sorted).
- Sorting logic depends on value type (text = alphabetical, number = numeric, Select/Multi-select = user-defined manual order). Sorting does not change which rows pass the filter.
- Grouping can "Hide empty groups" and hide/show individual groups; this is a display concern separate from filtering. But note: **sub-item visibility** settings *do* interact with filtered results if sub-items are enabled.

### 0.4 Filter UI/UX surface (chips, editing, removing)
- **Filter chips/pills** appear in a bar directly **above the table** (and above other layouts) once filters exist. Each chip shows the property + condition summary (e.g., `Status: Done`, `Due date: Is on or before Today`).
- **Quick-filter chips**: clicking a chip opens a small inline popover to change the value/operator without opening full settings. For Select/Multi-select/Status/Person, the chip often opens a checklist of options directly.
- **Adding**: Settings menu (top-right •••/⚙) → **Filter** → choose property; OR click **"+ Filter"** / **"+ Add filter"** in the filter bar. Advanced: **Filter → Add advanced filter**.
- **Editing**: click a chip → change property/operator/value inline.
- **Removing a single filter**: open the filter → **•••** → **"Delete filter"**. (Or click the **X**/remove on the chip.)
- **Removing all**: delete each, or via the advanced editor.
- Filters can be reordered by drag within the advanced editor.

## 1. Per property/field type — exact filter conditions

Notes on the tables below:
- **UI label** = the human-readable operator shown in the dropdown.
- **API key** = the machine identifier (authoritative enumeration; UI mimics it).
- Every type that can be blank exposes **"Is empty" / "Is not empty"** (`is_empty` / `is_not_empty`, value `true`).

| Contains | `contains` |

| Is not empty | `is_not_empty` |

Value: a single option name (`string`). (API also accepts `string[]` to match any of several.) The UI value picker is a single-choice list of the property's defined options.

### 1.4 Multi-select — `multi_select`

|---|---|

| Does not contain | `does_not_contain` |

Value: option name(s). "Contains" matches if the cell includes the chosen option(s).

### 1.5 Status — `status`
| UI label | API key |
|---|---|
| Is | `equals` |
| Is not | `does_not_equal` |
| Is empty | `is_empty` |
| Is not empty | `is_not_empty` |

Absolute operators plus a large relative set. Applies to `date` properties and (via timestamp) to Created/Last edited time.

| UI label | API key |

| Is before | `before` |
| Is after | `after` |

| Is empty | `is_empty` |
| Is not empty | `is_not_empty` |
| (Relative buckets) | `past_week`, `past_month`, `past_year`, `this_week`, `next_week`, `next_month`, `next_year` |

### 1.7 Person / People — `people`
Applies to **Person** properties and to **Created by** / **Last edited by** (all use the people condition).

| UI label | API key |
|---|---|
| Contains | `contains` |
| Does not contain | `does_not_contain` |
| Is empty | `is_empty` |
| Is not empty | `is_not_empty` |

Value: a user (UUID) or the special **`me`** value = the current user. The UI offers a person picker plus a **"Me"** shortcut. (`me` behavior differs for integration tokens — see API note.)

### 1.8 Files & media — `files`
| UI label | API key |
|---|---|
| Is empty | `is_empty` |
| Is not empty | `is_not_empty` |

Only empty/not-empty. No content matching.

### 1.9 Checkbox — `checkbox` (see §3)
| UI label | API key |
|---|---|
| Is (checked/unchecked) | `equals` |
| Is not | `does_not_equal` |

Value type: `boolean` (`true`/`false`). The UI shows a checked/unchecked toggle. **No** is_empty/is_not_empty (a checkbox is always either true or false).

### 1.10 URL — `url` (text condition set)
URL, Email, and Phone all use the **text/rich_text operator set**:

| UI label | API key |
|---|---|
| Is | `equals` |
| Is not | `does_not_equal` |
| Contains | `contains` |
| Does not contain | `does_not_contain` |
| Starts with | `starts_with` |
| Ends with | `ends_with` |
| Is empty | `is_empty` |
| Is not empty | `is_not_empty` |

### 1.11 Email — `email`
Identical operator set to URL (text set): Is, Is not, Contains, Does not contain, Starts with, Ends with, Is empty, Is not empty.

### 1.12 Phone — `phone_number`
Identical operator set to URL/Email (text set): Is, Is not, Contains, Does not contain, Starts with, Ends with, Is empty, Is not empty.

### 1.13 Created time — `timestamp: created_time`
Uses the full **Date** condition set (§1.6 / §2). In the API this is a timestamp filter (no property name; `timestamp: "created_time"` + a `created_time` date condition). Operators: Is, Is before, Is after, Is on or before, Is on or after, Is within, plus all relative options.
(Note: a created_time value is never truly empty, so Is empty/Is not empty are effectively no-ops.)

### 1.14 Last edited time — `timestamp: last_edited_time`
Same as Created time — full Date condition set. `timestamp: "last_edited_time"` + a `last_edited_time` date condition.

### 1.15 Created by — `people` (created_by)
Uses the **People** condition set (§1.7): Contains, Does not contain, Is empty, Is not empty. Supports `me`.

### 1.16 Last edited by — `people` (last_edited_by)
Uses the **People** condition set (§1.7): Contains, Does not contain, Is empty, Is not empty. Supports `me`.

### 1.17 Formula — `formula`
A formula filter **wraps the operator set of the formula's result type**. You first resolve the formula's output type, then apply that type's conditions.

| Formula result type | API sub-key | Operators available |
|---|---|---|
| Checkbox | `checkbox` | Is / Is not (`equals`, `does_not_equal`) |
| Number | `number` | full Number set (§1.2) |
| Text (string) | `string` | full Text set (§1.1) — Is, Is not, Contains, Does not contain, Starts with, Ends with, Is empty, Is not empty |
| Date | `date` | full Date set (§2) |

### 1.18 Relation — `relation`
| UI label | API key |
|---|---|
| Contains | `contains` |
| Does not contain | `does_not_contain` |
| Is empty | `is_empty` |
| Is not empty | `is_not_empty` |

Value: related page(s) (UUID). The UI shows a picker of related pages.

### 1.19 Rollup — `rollup`
Rollup filtering depends on the rollup's computed value type:

- **Array rollups** (show original / show unique): wrap a sub-condition with a quantifier:
  | UI intent | API key | Meaning |
  |---|---|---|
  | Any of them match… | `any` | at least one rolled-up value matches the inner condition |
  | All of them match… | `every` | every rolled-up value matches |
  | None of them match… | `none` | no rolled-up value matches |
  The inner condition can be **any other type's** filter condition (e.g. `any → rich_text → contains`).
- **Number rollups** (sum, count, average, etc. stored as number): wrap the **Number** condition set (`rollup → number → {…}`).
- **Date rollups** (Earliest date / Latest date / Date range): wrap the **Date** condition set (`rollup → date → {…}`).

### 1.20 ID (Unique ID / auto-increment) — `unique_id`
Numeric operator set:

| UI label | API key |
|---|---|
| = | `equals` |
| ≠ | `does_not_equal` |
| > | `greater_than` |
| ≥ | `greater_than_or_equal_to` |
| < | `less_than` |
| ≤ | `less_than_or_equal_to` |

Value: `number` (the numeric part; the text prefix is ignored for comparison).

### 1.21 Verification (wiki/verified pages) — `verification`
For verified databases (wikis):

| UI intent | API key | Accepted values |
|---|---|---|
| Verification status is | `status` | `verified`, `expired`, `none` |
| Verification status is not | `does_not_equal` | `verified`, `expired`, `none` |

## 2. Date filters — full detail

### 2.1 Absolute operators
When you pick an absolute date, you get:

| UI label | API key | Semantics |
|---|---|---|
| Is | `equals` | date property value equals the given date |
| Is before | `before` | strictly before |
| Is after | `after` | strictly after |
| Is on or before | `on_or_before` | ≤ given date |
| Is on or after | `on_or_after` | ≥ given date |
| Is within | *(UI range; §2.4)* | value falls in a relative range window |
| Is empty | `is_empty` | no date set |
| Is not empty | `is_not_empty` | a date is set |

Precision: when a time is included, comparison is millisecond-precise. No timezone provided → UTC (API); the UI uses the user's/workspace timezone.

### 2.2 Relative single-point date values
For **Is / Is before / Is after / Is on or before / Is on or after**, instead of a calendar date you can choose a relative anchor. The UI relative picker includes:

| UI label | Meaning | API relative string (where exposed) |
|---|---|---|
| Today | current date | `today` |
| Tomorrow | day after today | `tomorrow` |
| Yesterday | day before today | `yesterday` |
| One week ago | 7 days before today | `one_week_ago` |
| One week from now | 7 days after today | `one_week_from_now` |
| One month ago | 1 month before today | `one_month_ago` |
| One month from now | 1 month after today | `one_month_from_now` |
| One year ago | 1 year before today | *(UI; not in public relative-string list)* |
| One year from now | 1 year after today | *(UI; not in public relative-string list)* |

> The public API's documented relative strings are exactly: `today`, `tomorrow`, `yesterday`, `one_week_ago`, `one_week_from_now`, `one_month_ago`, `one_month_from_now`. The UI additionally offers year-based relative anchors. For clone parity, implement all of: today, tomorrow, yesterday, one week ago/from now, one month ago/from now, one year ago/from now.

### 2.3 Relative RANGE buckets (standalone operators)
These are self-contained operators (no value needed) that match a rolling window. API represents each as an empty object `{}`:

| UI label | API key | Window semantics |
|---|---|---|
| The past week | `past_week` | from 7 days ago up to now |
| The past month | `past_month` | from 1 month ago up to now |
| The past year | `past_year` | from 1 year ago up to now |
| This week | `this_week` | the current calendar week |
| The next week | `next_week` | now through 7 days ahead |
| The next month | `next_month` | now through 1 month ahead |
| The next year | `next_year` | now through 1 year ahead |

UI additionally surfaces (as part of the "is within" / relative bucket grouping) options phrased as **This week / Past week / Next week**, **Past month / This month / Next month**, **Past year / This year / Next year**. The API exposes `this_week` but does not document `this_month`/`this_year` as standalone empty-object operators — those are UI conveniences (implementable as a computed date range). For parity, implement the full matrix: Past / This / Next × Week / Month / Year.

### 2.4 "Is within" ranges
The **"Is within"** operator matches values inside a relative window and offers these choices in the UI:
- The past week
- The past month
- The past year
- The next week
- The next month
- The next year

Semantically identical to the `past_*` / `next_*` buckets but presented under a single "Is within" operator with a sub-menu. (Implement as: value ≥ window start AND value ≤ window end, where the window is computed from "now".)

### 2.5 Date filters on Created/Last edited time
Created time, Last edited time, Created by-time contexts all reuse the entire Date operator+relative machinery above.

## 3. Checkbox filter behavior

- A checkbox is **binary** — it is always either checked (`true`) or unchecked (`false`); it is never "empty".
- Operators (only two):
  - **Is** → `equals` (value `true` = checked, `false` = unchecked)
  - **Is not** → `does_not_equal`
- Because there is no empty state, **there is NO "Is empty" / "Is not empty"** for checkboxes.
- UI: the value selector is a checked/unchecked toggle (often shown as "Checked" / "Unchecked").
- Practical equivalences: `Is → Checked` == `Is not → Unchecked`.

## 5. Combining filters — full mechanics (expanded)

### 5.1 Structure
- A view's filter is a tree:
  - **Leaf** = one condition: `{ property, <type>: { <operator>: value } }`.
  - **Group** = `{ and: [ … ] }` or `{ or: [ … ] }` containing leaves and/or nested groups.
- Top-level default for simple filters = **AND** ("Where **all** of the following are true").
- Flip a group's connector between **"all" (AND)** and **"any" (OR)** via the connector dropdown shown between the first and second child.

### 5.2 Nesting depth
- **UI: up to 3 levels deep** (help doc: *"nested up to three layers deep"*).
- **Public API: documented up to 2 levels deep** for compound conditions. (Divergence — build the UI to 3.)

### 5.3 UI actions
- **Add filter** → new leaf at current level.
- **Add filter group** → new nested group (increments depth) with its own all/any connector.
- **••• on a filter → Add to advanced filter** → promotes simple bar to advanced editor.
- **••• on a filter → Delete filter** → remove that leaf.
- Drag handle (⋮⋮) → reorder conditions.

### 5.4 Header phrasing
- One or more simple filters ANDed: bar/editor header reads **"Where all of the following are true"**.
- Switched to OR at top level: **"Where any of the following are true"**.
- Each nested group repeats its own "all/any of the following are true" line.

## 6. Filters vs sorting vs grouping — interaction summary

- **Independent view settings**; each configured separately under View settings (Filter, Sort, Group, Sub-group).
- **Order of effect**: Filter decides visible rows → Group/Sub-group buckets those rows → Sort orders rows (within groups) and can order groups.
- Changing a filter never changes sort logic or grouping definitions (and vice versa), only the data each operates on.
- **Sort value logic** (context): Text = alphabetical; Number = numeric; Select/Multi-select = manual user-defined option order.
- **Grouping extras**: hide/show groups, hide empty groups, manual/alphabetical/ascending group order — display-only, orthogonal to filters.
- **Sub-items**: if sub-items are enabled, sub-item visibility settings additionally affect filtered results (documented caveat).

| Question | Answer |
|---|---|
| Are filters per-view? | **Yes.** Each view has independent filter settings. |

| "Save for everyone" ON | Filter saved on the view for all collaborators. |

## 9. Divergences to remember when cloning

1. **Nesting depth**: UI = **3 levels**; public API doc says 2. Build UI to 3.
2. **Relative dates**: API documents 7 relative strings (`today`, `tomorrow`, `yesterday`, `one_week_ago`, `one_week_from_now`, `one_month_ago`, `one_month_from_now`); the **UI adds year-based relatives and the This/Past/Next × Week/Month/Year matrix and the "Is within" range menu**. Implement the full UI matrix.
3. **Checkbox has no empty state** — only Is / Is not.
4. **Files & media** — only Is empty / Is not empty.
5. **URL/Email/Phone** all reuse the **text** operator set.
6. **Person, Created by, Last edited by** all reuse the **people** operator set (+ `me`).
7. **Created/Last edited time** reuse the full **date** operator set (as timestamp filters).
8. **Formula & Rollup** are polymorphic — resolve to the inner value type's operator set.
9. **Status** values may be individual statuses **or** status groups (To-do / In progress / Complete).
10. **Filters are per-view**, with a **"Save for everyone"** personal-vs-shared toggle.
